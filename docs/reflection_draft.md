# Team Reflection (DRAFT: rewrite in your own words before submitting)

> This draft was written from the project history so you have a starting point. The reflection is graded as your team's own thinking, so edit it, add your teammate's perspective, and replace anything that does not match your experience. Target: 300–500 words.

We built the E-Presso BI Analyst with Claude Code as our main AI development partner, and Gemini as the language model inside the app's assistant. Claude Code inspected the data files, wrote and explained each function, built the tests, and ran checks against our Power BI report. We worked one checkpoint at a time and asked it to explain each function in plain English so we could defend it.

Our biggest analytical challenge was getting the joins right. The data comes in three formats (an Access database, a tab-separated CSV and an Excel workbook), and the survey table looks like it should join to sales because both have a store and a year. Writing a grain statement for every table showed the problem: sales is one row per product, store and month, while the survey is one row per store per year. Joining them would repeat each satisfaction score 240 times. We kept the survey separate, joined only the many-to-one lookup tables, and wrapped every join in a merge check that compares rows and revenue before and after. That check also caught a deliberately duplicated store in our tests.

The biggest technical challenge was the assistant. Our first version answered "Which store had the greatest percentage decline?" with a ranking of total revenue: a real number, but for the wrong question. We found it by running the instructor's test questions, added functions that compare years, and retested. Testing also exposed Gemini's free-tier limit of 20 requests per model per day, which we diagnosed from the 429 error and handled with a backup model and a rules-based fallback.

The AI handled code, tests and documentation well, and it was fast at tracing errors. It struggled in places that needed context: it first chose a Gemini model that was no longer offered, and Gemini's explanations sometimes suggested analyses our data cannot support, like transaction counts. Human judgment was needed to decide that "channel" means store type, that blank survey scores must be excluded rather than counted as zero, that profit questions should be refused, and that the model should never state a number our code did not calculate. We enforced that last rule with a check on every number in Gemini's text.

We would trust this application for revenue reporting, because its totals match Power BI row for row and recalculate correctly when the data changes. We would not trust it for decisions such as closing a store. It has no costs, margins, leases or customer data, and correlation in the survey data does not establish cause. Before real use it would need cost data, user logins, a paid model tier with monitoring, and review of the assistant's answers by an analyst.
